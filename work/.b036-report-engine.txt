--- hyper-boosters#prerequisite  (CODE + ROW 3) ---
WHAT: new field `ClassFeature.requiresModification?: string[]` (src/rules/types.ts) — "any ONE of these
modifications must already be chosen"; read in `inventorModificationOptions` (src/rules/build.ts),
which gained an optional 5th parameter `chosen`. Both real callers now pass the character's three raw
modification picks: the built character's `validPick` (build.ts) and the builder's tier picker
(src/builder/shared.tsx). Omitted `chosen` stays ungated, so no third-party caller changes behaviour.
WHY (printed, innovation-5): "You must have the speed boosters modification to select this
modification." Nothing gated the pick, and hyper-boosters' `landSpeedBonus` is deliberately the +5
DELTA over speed-boosters' own +5 — so metallic-reactance (initial) + hyper-boosters (breakthrough)
was a legal build here that walked at +5 feet against a printed "+10-foot status bonus to your Speed".
Enforcing the prerequisite is what makes the delta encoding true, which is why the gate is the fix and
not a landSpeedBonus rewrite.
BLAST RADIUS: zero today — no shipped classFeature carries `requiresModification`. Once row 3 lands,
exactly one record changes: hyper-boosters is hidden from the breakthrough picker (and dropped from a
built character) unless speed-boosters is among the three picks. See CROSS-FILE GAP C for the five
siblings that print the same clause and are deliberately not authored here.
TEST: describe "hyper-boosters: the speed-boosters prerequisite" — three its on built inventors with
the row PATCHED INTO A CONTENT COPY IN MEMORY: the pick is dropped without speed-boosters; with it the
pick stands and the two halves of the delta sum to the printed +10 over the same character's own
unmodified land Speed; and a modification naming no prerequisite is untouched by the gate.

--- energy-resistant  (CODE ONLY) ---
WHAT: src/rules/derive.ts. New `etchedRuneDefences(inv, rune, db)` + two pushes in the DefenseGrants
inventory walk: every etched property rune on a row that passes `itemInUse`, and the Living Rune body
rune (which sits on no row at all, so every reader that walks `inventory[].runes` was blind to it).
The helper merges `RuneDef.passiveEffects` with the rune ITEM's resolved `effectChoices` grant,
reading the crafter's answer off the HOST row at `inv.effectChoices["<runeId>:<choiceId>"]` and

rune granted 0 against WG's real resistance 5. The first-option fallback is acid, which is exactly what
WG's own row grants, so an unrecorded pick is now WG-equal instead of empty.
BLAST RADIUS: every ARMOUR property rune whose payload is a defence now reaches its wearer once
etched. Measured in core.json today that is: energy-resistant / energy-resistant-greater (via the item
choice) plus the three runes that carry `passiveEffects` at all (assisting, trudds-strength,
sinister-knight). Nothing loses anything — the walk only adds sources, and it is inside the existing
`itemInUse` gate, so armour in the pack still protects nobody.
NOT DONE: no control writes the crafter's pick yet — see CROSS-FILE GAP B.
