WHERE THE READER WENT, AND WHY NOT build.ts / derive.ts
  The line names build.ts + derive.ts; the verifier's restatement adds "(or MainTab's action walk)",
  and that is where it landed, for one measured reason: buildCharacter never sees the whole action
  list. `Character.grantedActionIds` (build.ts:6212, applyAlwaysOn) carries only actions an ANSWER
  granted; a record's own `grantsActions` — arcane-bond's ['drain-bonded-item'] — is never resolved in
  build.ts at all. The single walk that unions record grants, ancestry/heritage/background grants,
  wielded-item grants and the answer-granted ids is MainTab.tsx:294. A suppression computed anywhere
  else would have had to be re-applied there anyway, and a second copy of the ownership rule is how
  the archSuppressed lane grew its duplicates.
  Shape: the array literal that fed `grantedActions` is now named `actionGranters`, read twice — once
  for `grantsActions` and once for `replacesActions` — then one `.filter(({id}) => !replaced.has(id))`
  before the limitedUses map. So the suppression is gated on OWNING the replacer for free, and a
  replacer that is itself gated (an item you are not wielding) suppresses nothing, exactly like its
  grant. Read through an inline cast, the same way explain.ts:293 reads `grantsActions`, so
  src/rules/types.ts is untouched — the engine family stages that file this batch.
