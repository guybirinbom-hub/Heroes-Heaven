WHAT WAS WRONG
  Five of the 129 stances carry no feat record at all — arcane-cascade, bullet-dancer-stance,
  claw-stance, talon-stance, tenacious-stance. Each lives in core.json `actions` and `stances`, and
  reaches a character through `grantsActions` on its granter (measured over core.json):
      feats/stalwart-defender-dedication  -> tenacious-stance
      feats/clawdancer-dedication         -> claw-stance, talon-stance
      feats/bullet-dancer-dedication      -> bullet-dancer-stance
      classFeatures/arcane-cascade        -> arcane-cascade
  MainTab.tsx built `stanceFeats` from `character.feats` alone, and `setActiveStance` has exactly one
  caller in the app — the chip inside that render loop. So no code path could put any of those five
  ids into `Character.activeStance`.

  The record that shows the cost: feats/unshaken-in-iron prints *"While in Tenacious Stance, you
  increase the value of your armor specialization effects by an amount equal to the value of your
  armor check penalty (adding +3 to the resistance while wearing plate armors, for example)."* The
  data (`armorSpec.bonusWhileStance = {stanceId:'tenacious-stance', source:'armorCheckPenalty'}`) and
  its reader in derive.ts (`c.activeStance === a.bonusWhileStance.stanceId`) were BOTH already
  correct — the guard was simply unreachable. Confirmed against print; WG delivers the same clause as
  an injectText on feat 26570, so there is no WG-vs-print conflict and no owner question is owed.

THE FIX  (src/sheet/MainTab.tsx, the `stanceFeats` const, now line 409)
  `stanceFeats` is now built from [...character.feats mapped to feats, ...grantedActions], put through
  the SAME predicate as before (a `content.stances[id]` entry plus either the `stance` trait or
  `form: true`), deduped by id, and narrowed to `{ id, name }` — the only two properties the three
  consumers (the chip label, `content.stances[f.id]` lookups, `formModesFor(f.id)`) ever read.
  `grantedActions` is the walk already computed at MainTab.tsx:313-336 for the Feat-actions list, so
  no new resolution logic was added and all five stances light up from the one widening. The dedupe
  matters because a stance feat that also grants a like-named action would otherwise render two chips.
  The comment above the const quotes the printed clause and names the five ids.

  A DATA row was rejected: minting feats/tenacious-stance would duplicate the action record its
  granter already points at, and would need the same duplicate four more times. The gap was the
  control, not the content.
