--- viking-vindicator#weapon-familiarity — AUTHORED (3 code edits, no row)
Finding id: viking-vindicator#weapon-familiarity (CONFIRMED). AoN feat-3619: "If you have Viking Weapon
Familiarity or Viking Weapon Specialist, add the bastard sword and rapier to the list of weapons in
those feats."
  1. src/rules/featGrants.ts — `requiresAnyFeat?: string[]` on the WeaponFamiliarity interface. The
     clause is a RIDER on a sibling feat's list; `skillsIfFeature` gates on a class FEATURE and the
     record's prerequisites name only Viking Dedication, so nothing existing could say it.
  2. src/rules/build.ts — one line at the head of the `for (const wf of clauses)` loop (the loop the
     verifier found the builder had NOT actually guarded). `feats` was already in scope.
  3. src/rules/featGrantsLane.ts — 'viking-vindicator' beside the frozen six-weapon
     'viking-weapon-familiarity' list, requiresAnyFeat ['viking-weapon-familiarity'].
GATE NARROWER THAN PRINT, deliberately and stated here: print names both viking feats, but Viking
Weapon Specialist carries no weaponFamiliarity of its own (it is a crit-spec feat, and FEAT_GRANTS has
no entry for it), so gating the PROFICIENCY half on it would grant a proficiency that feat never had a
list to extend. The crit-spec half of the same sentence is the engine spec's critSpecRequiresFeat row,
which does name both feats. This matches WG's own encoding of the proficiency half.
BLAST RADIUS: zero for every existing record — `requiresAnyFeat` is absent everywhere else and an
absent gate is a no-op; the background clause loop (build.ts:6728) is untouched because no background
carries the field. Pinned by the "a viking-less wizard gets nothing" assertion.

engine family's file list; they are named here because they are the same one-line predicate swap and
leaving them would have shipped a dead permission.

talismans and nothing else.

--- rusting-carapace#potency — AUTHORED (the lane: 108 rows)
Finding id: rusting-carapace#potency (CONFIRMED); its proposal ends "and the same for the other 111
specific magic armors as a lane", and both engine files filed that lane as DATA STILL NEEDED. No code:
the engine builder's readers (deriveAc's acItem floor and resilientSaveBonus's) are live and read
nothing today, because 0 armour records carry the field.
MEASURED by work/.b030-gap-armor-runes.mjs (in the spec's stage list), not guessed:
  - the lane is exactly the AoN mirror's `item_subcategory === "Specific Magic Armor"` — 182 docs;
  - `base_item` ("Leather Lamellar") is the ANCHOR the "+N …" phrase must reach, because a bare
    /\+[1-4]/ scan also matches "you gain a +1 circumstance bonus to AC", which is rusting-carapace's
    own second sentence;
  - the TEXT is each of our records' own description, never the mirror's: AoN files a whole variant
    family in ONE document and its opening sentence names the base variant's runes, so reading it gave
    victory-plate-greater a +1 where it prints +2, and the same for the four Wisp Chains, the five
    Plates of Yled, the three Library Robes and the Blade Byrnies. This is the family-head trap;
  - a description that is a raw AoN PAGE DUMP (the "Source … Usage … Base Armor" header) is skipped for
    the same reason — two duplicate records ship one (greater-mitigation-mail, greater-reactive-mail;
    the live twins mitigation-mail-greater / reactive-mail-greater are measured normally);
  - FUNDAMENTAL runes only. Property runes named in the same phrase (fortification, glamered,
    invisibility, deathless, antimagic…) are left out on purpose: ArmorRunes.property has no builtIn
    reader, so those would be dead rows.
CROSS-CHECK, run before authoring: for 104 of the rows the record's acBonus/dexCap are byte-identical to
the base armour's, i.e. our data never bakes the potency into the armour block, so no row double-counts.
The two that differ are a pre-existing defect of their own and are NOT rune-related, reported below.
COLLISIONS: items/rusting-carapace is deliberately absent — it is work/.b030-rows-engine.json's row, and
this measurement independently derives the same {potency:1} for it, which is the check that the parser
reads what a human read.
